# paper2patent 评估方案

用于判断 skill 的某次修改是否真的提高了专利初稿质量，而不只是让文件看起来更像专利。

只跑一篇论文、每个版本一次的对比，只能说明"这次哪份产物更好"。它不能说明哪个版本更稳定，更不能说明授权前景。

## 1. 固定条件

- 两个版本使用同一模型、同一输入文件、同一用户提示和同一预算，依赖材料（参考文件、脚本）完整可用。
- 每次运行记录 skill 版本（commit）、模型、耗时、token 和运行日志，否则无法把差异归因于 skill。
- 旧版只用它自己的文件运行，不混入新版的参考资料。

## 2. 输入集

`evals.json` 列出 5 篇公开论文，覆盖以下类型：

| 类型 | 主要考察 |
|---|---|
| 多智能体 LLM 系统 | 权利要求概括、充分公开 |
| 视觉模型结构 | 模型结构公开 |
| 音频生成 | 训练与推理流程 |
| 系统效率 | 技术性 |
| 时间序列预测 | 客体风险、公开状态 |

- 把 PDF 下载到 `evals/inputs/`，再用 `pdftotext -layout` 生成同名 `.txt`，供数值核对使用。
- 自己未公开的论文也可以加入，但只放在本地 `inputs/`，`inputs/` 和 `runs/` 已在 `.gitignore` 中。

## 3. 运行次数

- 每篇论文、每个版本至少运行 3 次。
- 结果放在 `runs/<eval-id>/<version>/run-<n>/`，目录内保存全部产物和 `final_message.md`。

## 4. 两层评估

**结构检查（自动）**

```bash
python evals/grade_structure.py --source evals/inputs/2308.00352.txt evals/runs/multi-agent-llm/new/run-*
```

- 检查内容：申请文件是否干净、权利要求布局、检查脚本的错误与范围类警告、交接清单、充分公开核查、是否编写了绕过脚本、数值能否在论文中找到。
- 结构检查只是门槛，不代表质量。

**质量评审（人工或模型盲评）**

- 按 `rubric.md` 的 9 个维度做成对盲评：A/B 随机命名，用模型评审时交换位置各评一次。
- 每篇论文取新旧各一次运行配对，至少评 3 对。

## 5. 结论规则

**可以说"新版更好"，需要同时满足：**

- 在维度 1（忠实度）、5（充分公开）、9（缺口交接）上不劣于旧版。在多数配对中，新版评为"更好"或"持平"的次数不少于"更差"的次数。
- 在其余维度中，新版在多数论文上胜出的维度多于落败的维度。
- 结构检查通过率不低于旧版。

**汇报要求：**

- 按维度报告胜、平、负，以及每个版本不同次运行之间的差异。
- 只在某一篇论文上出现的差异，单独说明，不外推。

## 6. 回归样例

每次修改脚本后，先用自带示例做冒烟测试（见 `CLAUDE.md`），再跑上述评估。
